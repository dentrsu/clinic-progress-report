1b
Drive Backup: JSON Dump → ZIP → Google Drive
GAS trigger • Daily / Weekly / Monthly rotation

All tables are dumped as JSON, zipped, and saved to a backup-tracker folder in Google Drive. Three rotation files overwrite themselves on schedule:

📆
backup-daily.zip
Every night at midnight
Always the freshest
📅
backup-weekly.zip
Every Sunday
Survives daily overwrites
📂
backup-monthly.zip
1st of each month
Longest retention

ZIP Contents

One .json file per table (18 total) + _manifest.json with timestamp, row counts, and error log.

Recovery Steps

  1. Download the ZIP from backup-tracker in Google Drive
  2. Extract JSON files
  3. Re-create schema by running SQL migrations in order
  4. Import each JSON into its Supabase table
  5. Oracle snapshots regenerate on next oracle_refresh_student()
💡 Retention: On a Wednesday you have 3 recovery points — today's daily, last Sunday's weekly, and the 1st of the month.
1c
Server Backup: Restic + pg_dumpall (Self-Hosted Supabase)
Cron • 02:00 daily • Full PostgreSQL dump → gzip → Google Drive via Restic

backup.sh on the Supabase server runs pg_dumpall from the supabase-db Docker container, compresses with gzip, and uploads to a Restic repository on Google Drive (gdrive:dentrsu-tracker). This is the most complete backup — it captures everything including auth schema, RLS policies, functions, triggers, and all databases.

Restore Commands

# List all snapshots restic -r rclone:gdrive:dentrsu-tracker snapshots # Restore latest snapshot to a directory restic -r rclone:gdrive:dentrsu-tracker restore latest --target /tmp/restore # Restore a specific snapshot by ID restic -r rclone:gdrive:dentrsu-tracker restore 0ceb4568 --target /tmp/restore # Decompress and apply to PostgreSQL gunzip -c /tmp/restore/*.sql.gz | docker exec -i supabase-db psql -U postgres # Verify repository integrity restic -r rclone:gdrive:dentrsu-tracker check
💡 Schedule offset: Restic runs at 02:00, GAS runs at midnight — two independent snapshots 2 hours apart, stored in different systems (Google Drive Restic repo vs Google Sheets/Drive ZIP).
⚠ Known issue: Duplicate log entries observed on 2026-03-26, suggesting the cron job may have fired twice. Ensure only one cron entry exists (crontab -l | grep backup) and consider adding a lock file (flock) to prevent concurrent runs.

Recovery Scenarios
⚡
Supabase Temporary Outage
Automatic. Circuit breaker switches to Sheets within 3 failed requests. Users keep working. Auto-resets when Supabase recovers.
🔧
Supabase Data Loss
Manual. Best: restic restore latest from gdrive:dentrsu-tracker → gunzip | psql (full schema + data + auth). Alternative: restore from Drive ZIP or Sheets backup + re-run SQL migrations.
⚙
Planned Maintenance
Admin action. Enable Maintenance Mode → traffic routes to Sheets. Perform work. Disable when done.
📊
Sheets Corrupted
Self-healing. Next nightly backup overwrites Sheets from Supabase. Or run backupAllTablesToSheets() manually.
💾
Bad Code Deploy
Git revert. Roll back to previous commit and redeploy to Apps Script.
⚠
Known Limitations
  • No point-in-time recovery — All backups are full snapshots. Changes between backups can be lost.
  • No automated reconciliation — Writes on Sheets during failover are not synced back to Supabase.
  • Oracle snapshots are derivable — If lost, they regenerate on next oracle_refresh_student(). No manual restore needed.
